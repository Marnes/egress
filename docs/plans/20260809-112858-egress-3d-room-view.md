# Egress — 3D room view (milestone 2)

**Status:** Completed

## Implementation summary

- Added the serializable visual schema, validator, industrial/snow themes, and authored pump-room
  visual to core; session bootstrap responses now deliver the visual and selected theme.
- Replaced the default room UI with a generic Three.js renderer featuring data-driven props,
  node/inspect cameras, active-node raycasting, informative canvas textures, outlines, occluders,
  grading, an explicit panel-lock display, and a facility computer terminal that mirrors the
  player/LLM message log.
- Added the `T` intercom, keypad entry, HUD, unread handling, lifecycle cleanup, `?theme=snow`, and
  the preserved `?ui=dom` debug client.
- Added a powered lighting path: the room starts dark under terminal glow, then server-owned power
  activates authored ceiling fixtures with PBR materials, soft shadows, bloom, and ACES grading.
- Added visual, API, scene-state, camera, interaction, visibility, and legibility regression tests;
  the workspace passes tests, type checking, linting, and the production build.

## Context

The MCP loop works end to end: an agent connects on a session code, polls `wait_for_player()`,
queries the record archive, and calls `release_panel_lock()`. The player side is a DOM list of
objects and buttons — fine as a test client, but it isn't the game.

This milestone replaces the room view with a Three.js one. Two constraints shape every decision:

1. **Nothing is hand-built for room 1.** Room 1 is hand-*authored* as a data spec; a generic
   `buildRoom(spec)` renders it. Procedural generation lands later and feeds the same function.
   Any code that knows "there are four pipes" is a bug.
2. **The renderer is theme-agnostic from day one.** Snow stations, orbital modules, flooded
   sections are coming. No lighting, fog, palette, or occlusion decision may be hardcoded for an
   industrial interior.

The server keeps owning puzzle state. The 3D layer is a pure view of `PlayerView` over SSE. No MCP
tool handler is touched.

## Decisions taken

| Question | Choice |
|---|---|
| Intercom hotkey | `T` opens; `Escape` closes; `T` also closes when focus is not in the input |
| Existing DOM view | Kept behind `?ui=dom` as a debug harness, not deleted |
| Snow legibility gate | `?theme=snow` dev override swaps room 1's theme at build time |
| Cross-node clicking | No shortcut travel targets; WASD/drag controls movement and only nearby enabled props raycast |
| Visual spec delivery | Over the wire in the session payload, not imported into the web bundle |
| Intercom pausing | Nothing pauses (agreed — see *Intercom overlay*) |

**Visual spec delivery is the one I decided for you, and it matters.** `RoomSpec` is not
serialisable (`isComplete`, `needs`, `inspect` are functions) but `RoomSpec.visual` is pure data by
construction. Once generation produces a room per session, the browser cannot import the spec — it
must arrive from the server. So build that seam now: `GET /api/session/:code` returns
`{ code, view, visual, theme }`. SSE keeps carrying only `view`. Static spec once, dynamic view
continuously.

## The schema

New directory `core/src/visual/`, zero dependencies, no Three.js types, JSON-round-trippable.

### `core/src/visual/types.ts`

```ts
export type Vec3 = [number, number, number];
export type Hex = string;                    // "#rrggbb", validator-enforced

export type Transform = {
  position: Vec3;
  rotation?: Vec3;                           // Euler XYZ radians, default [0,0,0]
  scale?: Vec3 | number;                     // default 1
};

/** Closed set of colour ROLES. Props reference roles; a hex in a prop is a validation error. */
export type PaletteRole =
  | 'background' | 'floor' | 'wall' | 'ceiling'
  | 'structure' | 'metal' | 'metalDark' | 'accent' | 'warning' | 'ink';

export type Palette = Record<PaletteRole, Hex>;

export type Fog = {
  color: Hex;
  /** Metres at which a surface is ~95% obscured. Scale-relative; density derived at build. */
  visibilityM: number;
  mode: 'exp2' | 'linear';
};

export type LightRig = {
  ambient: { color: Hex; intensity: number };
  hemisphere?: { sky: Hex; ground: Hex; intensity: number };
  /** `direction` is the direction light travels, world space, normalised at build. */
  directional?: { color: Hex; intensity: number; direction: Vec3 }[];
  points?: { color: Hex; intensity: number; position: Vec3; reachM: number }[];
};

/** Every theme limits what the player can see at once. Same gameplay job, different expression. */
export type OccluderSpec =
  | { kind: 'lightCone'; angleDeg: number; penumbra: number; intensity: number;
      reachM: number; color: Hex; ambientFloor: number }
  | { kind: 'whiteout'; driftMps: number; particleCount: number; color: Hex; gustHz: number }
  | { kind: 'visor'; fovDeg: number; vignetteInner: number; vignetteOuter: number; glare: number }
  | { kind: 'turbidity'; causticsHz: number; swayM: number; color: Hex };

export type OutlineSpec = {
  thicknessPx: number;          // CSS px, scaled by devicePixelRatio at runtime
  depthSensitivity: number;
  normalSensitivity: number;
  // No colour field: the outline is always palette.ink, and the validator enforces
  // that ink has sufficient contrast against every other role in the palette.
};

export type Theme = {
  id: string;
  palette: Palette;
  fog: Fog;
  lightRig: LightRig;
  occluder: OccluderSpec;
  outline: OutlineSpec;
  surface: { shading: 'flat' | 'smooth'; roughness: number; metalness: number };
  grade: { vignette: number; grain: number; exposure: number };
};

export type NavNode = {
  id: string;
  label: string;                // descriptive viewpoint label
  position: Vec3;               // eye position, y === RoomVisual.eyeHeightM
  lookAt?: Vec3;                // omitted => centroid of props assigned to this node
};

export type InspectPose = {
  anchor?: Vec3;                // omitted => prop's world bounding-sphere centre
  normal?: Vec3;                // omitted => direction from owning node toward anchor
  distanceM?: number;           // omitted => derived from bounding sphere and fovDeg
  fovDeg?: number;              // default 30
};

export type PropSpec = {
  id: string;
  type: string;                 // prop-registry key
  transform: Transform;
  parent?: string;              // another prop id; transform becomes relative
  /** Nav nodes that render (and, if interactive, can click) this prop.
   *  Omitted = always-visible scenery: shell, floor, structure. */
  nodes?: string[];
  /** The ONLY link to gameplay: a RoomSpec.objects[].id. */
  objectId?: string;
  interactive?: boolean;
  inspect?: InspectPose;
  /** Prop-type-specific slot name -> palette role. */
  materials?: Record<string, PaletteRole>;
  /** Prop-type-specific scalars. No colours, no ids. */
  params?: Record<string, number | string | boolean>;
};

export type RoomVisual = {
  version: 1;
  bounds: { size: Vec3 };       // interior extents; origin is floor centre
  eyeHeightM: number;
  themeId: string;
  startNodeId: string;
  nodes: NavNode[];
  props: PropSpec[];
};
```

`core/src/types.ts` gains one line: `visual: RoomVisual;` on `RoomSpec`.

### Four schema choices that differ from your sketch, and why

- **`nodes: string[]`, not `node: string`.** A generated pipe run will be visible from two
  viewpoints. Singular `node` forces duplicate props with different ids the moment that happens.
- **`materials: Record<slot, PaletteRole>`, not colours.** This is what actually makes "same
  meshes recoloured reads as a different world" true. A prop that can name a hex will eventually
  name one, and then one room resists retheming.
- **`fog.visibilityM`, not `fogDensity`.** Density is scale-dependent: a density tuned for a 6×4m
  room whites out a 20m hangar. Visibility in metres survives generation; the build derives
  `density = 3 / visibilityM` for exp2.
- **No `dynamic` flag.** Whether a prop redraws is a property of its *type* (a gauge always reads
  its value from the view), not of the instance. A per-instance flag is a way to author a gauge
  that silently never updates. Instead: `informative` behaviour lives in the factory, and the
  legibility module is the only thing that draws glyphs.

### `core/src/visual/validate.ts`

```ts
export type Issue = { level: 'error' | 'warn'; path: string; message: string };

export function validateRoomVisual(
  v: RoomVisual,
  ctx: { objectIds: readonly string[]; propTypes: readonly string[]; themes: readonly Theme[] }
): Issue[];
```

Errors: duplicate prop/node ids; unknown `themeId`; unknown `type` (against the registry keys the
web layer passes in); unknown `parent`; parent cycles; unknown `nodes[]` entry; `objectId` not in
`RoomSpec.objects`; `startNodeId` unknown; any hex string inside `params`; malformed hex anywhere;
node `position.y !== eyeHeightM`; prop or node outside `bounds`; `interactive: true` with no
`objectId`; ink/palette contrast below threshold (WCAG-style relative luminance, ~20 lines, no deps).

Warnings: prop with `interactive: true` but no node (unreachable); node with no props assigned;
node with no `lookAt` and no props to derive one from; two nav nodes closer than 0.5m.

Run it in a vitest case over every shipped room, and again in `buildRoom` in dev builds. This is
the thing that will catch generated rooms before they render as a black screen.

### Themes

`core/src/visual/themes.ts` exports `themes: Record<string, Theme>` with **`industrial`** and

## Informative surfaces — the one function

`web/src/three/textures/legibility.ts`. This module owns three constants and never reads a theme:

```ts
const FACE = '#e8e6e0';   // near-white
const INK  = '#101214';   // near-black
const HALO = 'rgba(8,9,11,0.78)';

export type LegibilityKit = {
  /** Off-screen canvas + CanvasTexture, redrawn only when `value` changes. */
  glyphPanel(opts: { widthPx: number; heightPx: number; aspectM: [number, number] }): GlyphPanel;
};

export type GlyphPanel = {
  texture: THREE.CanvasTexture;
  material: THREE.MeshBasicMaterial;   // fog: false, toneMapped: false
  /** No-op when `value` is unchanged. */
  draw(value: string | null, style: 'dial' | 'stencil' | 'display'): void;
  dispose(): void;
};
```

Three details do the actual work:

- **`fog: false` and `toneMapped: false`.** A `MeshBasicMaterial` still gets fogged by default. In
  a `visibilityM: 4` snow room, a fogged gauge face is a white rectangle. This single flag is the
  difference between the snow room working and not.
- **Halo before glyph.** Every glyph is stroked in `HALO` at ~8% of cap height, then filled in
  `INK`. That is what survives a bright fog colour bleeding through at the edges.
- **The occluder does not touch these.** The light-cone occluder dims unlit materials; a
  `MeshBasicMaterial` is unaffected by lights by definition, so this is free — but it must stay
  true when the whiteout occluder adds a fullscreen fade. Whiteout applies its fade in the
  composer *before* an "informative" stencil-masked restore. Simpler alternative if that proves
  fiddly: cap the whiteout's screen-space fade at 0.85 so glyphs never fully wash out.

Prop factories never call `ctx.fillText`. If a prop needs to show information, it asks for a
`glyphPanel`. That is the enforcement.

## Prop registry

export type PropContext = {
  spec: PropSpec;

## `buildRoom`

`web/src/three/buildRoom.ts`. Signature and behaviour, in order:

```ts
export function buildRoom(visual: RoomVisual, theme: Theme, deps: BuildDeps): RoomHandle;

export type RoomHandle = {
  scene: THREE.Scene;
  nodes: Map<string, NavNode>;
  props: Map<string, PropInstance>;
  /** hitboxes for the active node */
  activeHitboxes(): THREE.Object3D[];
  setActiveNode(id: string): void;
  applyView(view: PlayerView): void;
  occluder: OccluderInstance;
  dispose(): void;
};
```

1. `validateRoomVisual` in dev; throw on any error.
2. Build `ThemeRuntime`: one cached `MeshStandardMaterial` per `PaletteRole`, `flatShading` from
   `theme.surface.shading`, roughness/metalness from `theme.surface`.
3. `scene.background = palette.background`; `scene.fog` from `theme.fog` with density derived from
   `visibilityM`.
4. Lights from `theme.lightRig`. Nothing else creates a light except the occluder.
5. `occluderRegistry[theme.occluder.kind](theme.occluder, ctx)` → `OccluderInstance`
   (`{ object?, update(dt, camera), composerPass?, dispose() }`). Same registry pattern as props;
   `lightCone` and `whiteout` implemented, `visor`/`turbidity` stubs that throw a clear error.
6. Topologically sort props by `parent`, instantiate via `propRegistry[type]`, attach to parent's
   `object` or the scene, apply transform.
7. Index props by node. Compute each node's `lookAt` if absent (centroid of its props). Compute
   each interactive prop's `InspectPose` defaults from its world bounding sphere.
8. Expose authored nodes to the camera controller as initial and inspection-return viewpoints.
9. `setActiveNode` flips `object.visible` per node group and swaps the raycast set.
10. `applyView` walks `props` and calls `update?.(view)`.

There is no room-1 branch anywhere in this file. The `if` statements are on `theme.occluder.kind`
and `prop.type`, both registry lookups.

## State ownership — where the line is

**Server owns, and the 3D layer only reads:** `panelLocked`, `switches[]`, `powerOn`,
`keypadLockoutRemainingMs`, `doorOpen`, `complete`, and `objects[].gauge` — which is already `null`
until power is on, so the browser is *structurally incapable* of rendering a gauge digit early. Keep
that property; it's the same trick as `AgentSafeText`, applied to the player side.

**The 3D layer owns:** `activeNodeId`, camera mode and tween progress, hover target, intercom open
state, unread count, last-drawn texture value. All of it is "where you are standing and looking".

**The test:** if closing and reopening the tab must reproduce it, it's server state. Everything else
is client state.

**The path from SSE to a material**, concretely:

```
POST /api/session/:code/action          (unchanged; web/src/lib/api.ts sendAction)
  -> applyToSession() -> applyAction()  (server, single writer)
  -> broadcastState() -> SSE 'state'    (unchanged)
  -> connectEvents onState              (unchanged; web/src/lib/sse.ts)
  -> App.svelte  view = v               ($state)
  -> $effect     room.applyView(view)
  -> PropInstance.update(view)          -> lever.rotation.x, material swap, glyphPanel.draw(...)
```

Every arrow already exists except the last two. No new server endpoints, no new SSE events.

**The rule for prop authors:** a prop may hold *animation* state (tween progress, last-drawn
value) but never *authoritative* state. Every branch reads `view`. Enforce with a vitest case over
a headless build: `applyView(a); applyView(b)` must produce the same scene-graph snapshot as
`applyView(b)` on a fresh build, and `applyView(v)` twice must be a no-op the second time.

Clicking a prop does two independent things: it moves the camera locally (client state), and it
POSTs the object's action (server state). Clicking a gauge still POSTs `inspect`, because
*"Gauge C reads 9."* in the room log is what the player reads to the agent, and that line must stay
server-authored.

## Camera: nav and inspect

One state machine in `web/src/three/camera.ts`:

```ts
type CameraState =
  | { mode: 'node'; nodeId: string }
  | { mode: 'transit'; from: Pose; to: Pose; t: number; then: CameraState }
  | { mode: 'inspect'; propId: string; returnNodeId: string };
```

- `Pose = { position: Vector3; quaternion: Quaternion; fov: number }`.
- Transit lerps position, slerps quaternion, and lerps FOV, over ~550ms with a
  `smootherstep` ease. FOV is part of the pose so inspect gets a "lean in" for free.
- Inspect pose is *derived by default*: camera sits at `anchor + normal * distanceM`, looking at
  `anchor`, with `distanceM = boundingSphere.radius / tan(fovDeg/2 * DEG) * 1.15`, clamped to
  `[0.28, 1.4]`. Spec overrides only where the default is wrong. **This is the part that must not
  be hand-authored per prop, or generation dies.**
- Escape precedence, explicitly: intercom open → close intercom. Else inspecting → return to node.
  Else nothing.
- Only the active node's hitboxes raycast. Nav discs always raycast.

At inspect distance a 0.15m gauge face at 30° FOV spans roughly 40% of viewport height — around
400px on a 1440×900 laptop. Glyph size is not the legibility risk; contrast and fog are, which is
what step 5 gates on.

## Outline pass

Screen-space edge detection on depth + normals. `web/src/three/passes/OutlinePass.ts`.

**Technique.** Two geometry passes plus one fullscreen pass:

1. `RenderPass` → beauty target.
2. Normal/depth prepass: a `WebGLRenderTarget` with an attached `THREE.DepthTexture`, rendered with
   `scene.overrideMaterial = new THREE.MeshNormalMaterial()`.
3. `ShaderPass` sampling `tDiffuse`, `tNormal`, `tDepth`. Roberts-cross on linearised view-space
   depth (`perspectiveDepthToViewZ` from three's `packing` shader chunk) plus a dot-product term on
   normals. Composite `palette.ink` where either term crosses threshold.

Two details that decide whether it looks right:

- Scale the depth threshold by view-space Z, and suppress depth edges on surfaces whose normal is
  near-perpendicular to view. Without this you get outlines crawling across the floor at grazing
  angles and no outlines at all on distant geometry.
- Multiply the sample offset by `devicePixelRatio` so `thicknessPx` means CSS pixels and the line
  doesn't halve on a retina display.

**Cost.** One extra full-scene draw (`overrideMaterial`, so one material, good batching) plus one
fullscreen pass at native resolution. For a room of ~40 meshes at 1080p this is single-digit
milliseconds on integrated graphics. It is resolution-bound, not prop-bound, which is the right
scaling behaviour for generated rooms. Do **not** run the prepass at half resolution — 1px lines
need full res.

**Rejected:** three's built-in `OutlinePass` is selective per-object glow, not what's wanted.
Inverted-hull is per-mesh (cost scales with prop count), misses interior edges, and breaks on thin
geometry — keep it in the back pocket for a single stubborn GLTF prop, not as the system.

**Optimisation if prop counts explode:** WebGL2 MRT (`WebGLRenderTarget(w, h, { count: 2 })`) to
write colour and normals in one pass. It requires every prop material to be a custom
`ShaderMaterial`, which fights the palette-role material cache. Not now; note it exists.

The outline colour is always `palette.ink`, and the validator enforces ink's contrast against every
other role. That is what makes it palette-independent *by construction* rather than by discipline.

## Intercom overlay

`web/src/ui/Intercom.svelte` + `web/src/ui/input.ts`.

**Hotkey: `T`.** Twenty years of multiplayer convention (Quake, Source, Minecraft) for "open chat",
and unlike `E` or `F` it is never an interact key, so it stays free as the world verb set grows.
Opens with `T`, closes with `Escape`, and also closes with `T` when focus is not in the input
(i.e. the player clicked the canvas while the overlay was up). Full same-key symmetry is
impossible while a text field has focus — a plain letter either types or toggles, not both.

**Input mode router** (`input.ts`), one global `keydown` listener with an explicit mode:

```ts
type InputMode = 'world' | 'text';
```

`world` routes movement/interaction hotkeys; `text` routes only `Escape` and lets everything else
reach the input. Mode is set by the overlay's open state, not inferred from `document.activeElement`
— inference breaks the moment focus lands somewhere unexpected. Raycast click handling checks the
same mode, so a stray click behind the overlay can't flip a breaker mid-sentence.

**Focus.** Input gets `.focus()` in an `$effect` on open. On close, focus returns to the canvas,
which carries `tabindex="0"` for exactly this reason.

**Unread.** The SSE `intercom` handler increments `unreadCount` when `from === 'agent' && !open`;
opening clears it. A small always-visible corner affordance shows the speaker glyph, the `T` hint,
and a dot when unread. It is DOM, over the canvas, like everything puzzle-critical.

**Log persistence.** `intercomLog` already lives in `App.svelte` state, above the overlay
component, and nav nodes don't touch it. Nothing to do beyond not moving it.

**On pausing: I agree, and here is the reason plus the one cost.** The lockout timer is
server-owned and pushed over SSE; pausing it would need a server-side pause concept, which means
the server would know whether the player has the intercom open — that's a new piece of session
state leaking into the game model for no gameplay gain. Diegetically it's a two-way radio, not a
menu. The cost lands later: a timed trap that kills the player mid-sentence will feel unfair. The
mitigation is a constraint on the overlay now — **it occupies the bottom third and is never a
full-screen modal**, so the room stays visible and a trap firing is always legible. Build it that
way from the start; retrofitting a modal into a non-modal is a rewrite.

## Build order — one real correction, one reshuffle

**Your step 6 must come before your step 5.** The step-5 gate is *"can I read C and 9 in both the
industrial theme and a white snow palette?"* — that test cannot be run before the theme rig exists.
As written, step 5 gates on something step 6 provides.

The fix isn't just a swap. The *palette/fog/light* half of the theme rig belongs in step 1: the
greybox should read its colours from `theme.palette` on day one, because retrofitting "no hardcoded
colours" across ten prop factories later is precisely the failure mode you're trying to avoid. Only
the *occluder* half is genuinely later work.

Revised:

## What breaks when generation starts

Ranked by how much they'll cost to fix later.

1. **Fog and occluder ranges in absolute units.** Already handled: `visibilityM` and `reachM` are
   metres. Keep every future range field in metres, never in raw density or attenuation constants.
2. **Hand-authored `lookAt` and `InspectPose`.** Both have derivation defaults in this design. Use
   them for room 1 wherever the default is acceptable, so the derivation is exercised now rather
   than discovered to be wrong on the first generated room. The four pipe inspect poses above are
   overrides mainly to show the shape — try deleting them first.
3. **Nav-graph reachability.** A generated prop assigned to no node is invisible and unsolvable.
   The validator warns today; make it an *error* the moment generation lands.
4. **Draw calls.** Room 1 has ~40 meshes; the outline prepass doubles the geometry passes. A
   generated 300-prop room needs static non-interactive geometry merged per material at build time
   (`BufferGeometryUtils.mergeGeometries`). `buildRoom` should grow a merge step, not each factory.
5. **One `CanvasTexture` per informative surface.** Fifty gauges is fifty textures and fifty
   canvases. `LegibilityKit` should own a pool and, eventually, an atlas. Design it as a kit now
   (which is why it isn't a bare function) so the pooling change is internal.
6. **Palette role exhaustion.** Ten roles is enough for a pump room and probably not for a
   greenhouse. Adding a role is a breaking change to every theme. Add roles in deliberate batches,
   and never let a prop fall back to a hex when its role is missing — fail validation instead.
7. **Occluder kinds are bespoke code.** A generated room *selects* an occluder kind; it must never
   need a *new* one. Keep the set small and closed, and treat "this theme needs a new occluder
   kind" as a design review, not a ticket.
8. **Room size vs. camera near/far and shadow ranges.** Derive both from `bounds` in `buildRoom`;
   don't let a constant leak in that's tuned for 6×4m.
9. **Prop `params` are untyped scalars.** Fine while a human authors them; a generator will emit a
   wrong key and get a silently default-sized box. Add per-type param schemas to the registry
   (`{ factory, paramSchema }`) and validate them when generation lands.
10. **`shell` assumes a rectangular box.** An L-shaped or multi-room generated space needs either a
    different `shell` type or a wall-segment prop list. Not a problem now; don't build anything
    that assumes exactly six planar surfaces.
